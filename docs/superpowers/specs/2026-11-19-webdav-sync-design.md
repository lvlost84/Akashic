# WebDAV 암호화 동기화 설계 (1단계)

## 목적
폴더를 클라우드 동기화 클라이언트에 맡기는 현재 방식 대신, 사용자의 NAS에 둔 WebDAV 서버(도커 + HTTPS 리버스 프록시)로 앱이 직접 동기화한다. 서버는 내용을 볼 수 없어야 한다(종단간 암호화). 집 밖 인터넷에서도 쓴다.

## 목표 / 비목표
- 목표: WebDAV 서버 동기화, 앱에서 암호화, 저장소별 키(중복 저장소 방지), 기기 추가는 복구 문자열 입력, 동시 업로드 충돌 감지.
- 비목표(2단계 이후): "이 앱만 접속 가능"(전용 서버 필요, WebDAV로는 불가), 서버 쪽 챌린지-응답 인증, 문서 단위 동기화·병합, 키 교체, 비밀번호/키의 DPAPI 보호.
- 하지 말 것: 서버에 암호화 키나 평문을 보내는 것. 기존 폴더 동기화 동작을 바꾸는 것.

## 접근 (선택됨)
스냅숏 조각 업로드(A안)를 WebDAV 전송으로 옮긴다. 문서 단위 동기화(B안)와 전용 서버(C안)는 비용이 커서 1단계에서 제외했다. 동기화 로직과 전송을 분리(`Remote`)해 두므로 나중에 전송만 바꿀 수 있다.

## 설계
**키**: 저장소를 만들 때 무작위 32바이트 마스터 키를 만든다. 사용자에게는 체크섬이 붙은 복구 문자열(예: `AKS1-XXXX-...`)로 보여 주고, 만든 직후 한 번 크게 안내한다. HKDF-SHA256으로 용도별 키를 파생한다.
- `vault-id` → 서버 폴더 이름 `akashic-<hex>`. 같은 키는 같은 폴더이므로 저장소가 중복으로 만들어지지 않고, 이미 있으면 "연결"로 처리한다.
- `enc` → XChaCha20-Poly1305 암호화 키.
서버는 vault-id(폴더 이름)와 암호문만 안다. 마스터 키·enc 키는 서버로 가지 않는다.

**서버 배치** `<기본 URL>/akashic-<vault-id>/`
- `manifest` : 암호화된 manifest(세대, 기기, 저장 시각, 조각 목록과 각 조각의 평문 해시·길이).
- `<세대>.<번호>.part` : 암호화된 512KB 조각. 이름은 현재 방식과 같은 규칙. 조각별 무작위 nonce, AAD에 vault-id·세대·번호를 넣어 조각 바꿔치기를 막는다.
- 안 바뀐 조각은 manifest의 평문 해시로 알아보고 다시 올리지 않는다.

**충돌 방지**: 잠금 파일 대신 manifest를 `If-Match: <읽을 때의 ETag>`로 올린다(최초는 `If-None-Match: *`). 412가 오면 "다른 기기가 먼저 올렸습니다"로 올리기를 중단하고 받아오기를 안내한다. 조각은 manifest보다 먼저 올리므로 도중에 끊겨도 마지막 정상 저장본이 유지된다(현재와 같음). 연결 시험에서 서버가 ETag를 주고 If-Match를 지키는지 임시 파일로 확인하고, 지키지 않으면 설정을 거부한다.

**키 확인**: 동기화 시작 때 manifest를 내려받아 복호화한다. 실패하면 "키가 다릅니다"로 멈춘다(서버에 무엇도 쓰지 않는다).

**전송**: 새 HTTP 크레이트 없이 기존 업데이트처럼 Windows `curl.exe`를 쓴다(`--proto =https`, 비밀번호는 명령줄이 아니라 `-K -` 표준입력 설정으로 전달해 프로세스 목록에 노출되지 않게 한다). 암호는 `chacha20poly1305`·`hkdf`·`hmac`·`getrandom` 크레이트(RustCrypto, 순수 Rust)를 추가한다.

**구조**: `Remote` 트레이트(get / put(if_match) / delete / list)와 `FolderRemote`(기존) · `WebDavRemote`(새) 구현. 암호화·manifest·조각 로직은 `Remote` 위에서 동작하는 새 모듈 `vault.rs`(순수 로직, 테스트 대상). 기존 `sync.rs`의 폴더 방식은 그대로 둔다.

**UI**(`sync_ui.rs`): 동기화 방식 선택(폴더 / WebDAV). WebDAV: URL·사용자·비밀번호, [연결 시험], [새 저장소 만들기](복구 문자열 표시·복사), [기존 저장소 연결](복구 문자열 입력). 이후 올리기·받아오기·자동 확인은 기존 흐름을 그대로 쓴다.

## 인터넷 노출 대비(사용자 쪽 서버 설정 문서로 제공)
리버스 프록시에서 HTTPS 강제, 요청 크기 제한, 로그인 실패 제한(fail2ban 등), WebDAV 전용 계정(경로 한정), NAS 스냅샷 백업(계정이 털려 삭제돼도 복구). 도커 compose 예시를 `docs/`에 둔다.

## 검증 계획
- 단위 테스트: 암호화·복호화 왕복, 틀린 키 거부, 조각 변조 거부, 조각 바꿔치기 거부, 복구 문자열 체크섬 오류, 키→vault-id 결정성, 가짜 `Remote`로 412 충돌·중단 후 복구·안 바뀐 조각 건너뛰기.
- 통합: 로컬에 WebDAV 서버를 띄워 실제 `curl.exe` 경로로 올리기/받아오기/충돌 확인(서버 종류는 구현 때 확인, 사용 가능한 것이 없으면 그 사실을 보고하고 미확인으로 남긴다).

## 구현에 맡기는 부분
조각 크기 재사용(512KB), 복구 문자열 표기 형식, 오류 문구, 재시도 간격.

## 결정이 필요한 것(기본값을 정해 둠)
1. 복구 문자열과 WebDAV 비밀번호를 `config.json`에 평문으로 저장(기본). 이 PC를 누가 열면 보이므로 DPAPI 보호는 후속 과제.
2. WebDAV 방식은 항상 암호화(암호화 끄기 옵션 없음).
3. 기존 폴더 동기화는 유지.
