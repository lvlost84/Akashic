# 문서 단위 동기화 설계 (WebDAV, 서버 로직 없음)

## 목적
지금의 WebDAV 동기화는 DB 전체 스냅숏이라 두 PC가 같은 시간대에 서로 다른 문서를 고치면 한쪽이 통째로 버려진다. 문서(와 분류·태그) 단위로 주고받아 **서로 다른 문서의 동시 편집은 자동으로 합치고**, 같은 문서의 동시 편집은 가능한 한 합치되 안 되면 **둘 다 남긴다**.

## 전제(가장 중요한 제약)
- 서버는 일반 WebDAV(시놀로지 Apache 등)다. 병합·순번·알림 같은 서버 로직이 **없다**. 파일 올리기·읽기·목록·삭제와 "없을 때만 쓰기"(If-None-Match)만 믿는다. 모든 판단과 병합은 **각 PC의 앱**이 한다. (서버가 병합하는 구조의 앱을 참고 대상으로 삼지 않는다.)
- 종단간 암호화 유지: 서버는 암호문만 본다. 기존 `vault.rs`의 키·암호화를 재사용한다.
- 기존 스냅숏 동기화는 그대로 둔다(새 방식은 별도 저장소 형식).

## 목표 / 비목표
- 목표: 바뀐 문서만 올리기·받기, 서로 다른 문서의 동시 편집 자동 반영, 같은 문서 충돌 시 자동 3-way 병합 → 안 되면 충돌 사본, 삭제·분류 이동·태그·핀·휴지통 전파, 이미지 중복 없는 전송, 오프라인 편집 후 나중에 동기화.
- 비목표: 실시간 공동 편집, 글자 단위 CRDT(후속 가능), 자체 서버, 모바일.
- 하지 말 것: 서버에 키·평문, 동기화 중 데이터를 조용히 잃는 것(충돌은 반드시 사본으로 남긴다).

## 접근
- **A. 문서 단위 최신 우선 + 자동 3-way 병합(권장)**: 문서마다 마지막으로 동기화한 상태(base)를 로컬에 둔다. 양쪽이 바뀌었으면 base·내것·상대것으로 필드별, 본문은 줄 단위 3-way 병합한다. 겹치지 않게 고쳤으면 자동 병합, 같은 줄을 서로 다르게 고쳤으면 충돌 사본. 새 크레이트 없음.
- B. 본문 글자 단위 CRDT(yrs 등): 같은 문서도 글자 단위로 항상 합쳐지지만, egui `TextEdit`의 커서·되돌리기와 CRDT 상태 불일치 위험, 의존성 증가가 크다. 같은 문서를 같은 순간에 고치는 일이 드물다면 비용 대비 이득이 작다.
- C. 문서 단위 + 충돌 사본만(병합 없음): 가장 단순하지만 같은 문서를 다른 줄에서 고쳐도 사본이 생겨 불편하다.
- 선택: A. 데이터 모델에 base를 이미 두므로 나중에 본문만 B로 올리는 길도 막히지 않는다.

## 데이터 모델 (DB 스키마 v4)
- 문서·분류·태그마다 **전역 고유 ID `uid`**(무작위 128비트, `getrandom`)를 추가한다. 정수 `id`는 PC 로컬용으로 유지(위키 링크는 제목 기반이라 영향 없음).
- 동기화 필드: `ver`(Lamport 카운터), `dev`(마지막으로 쓴 기기 ID), `dirty`(마지막 동기화 이후 바뀜), `base_json`(마지막으로 동기화한 전체 상태 JSON).
- 삭제(영구 삭제)는 `tombstones(uid, ver, dev)`로 남긴다. 휴지통은 일반 필드.
- 이미지는 이미 해시로 식별되므로 내용 주소 파일로 전송한다.
- 문서 레코드(JSON): `uid, title, body, category_uid, tag_uids[], pinned, trashed_at, created, updated, ver, dev`.

## 서버 배치 `akashic2-<vault-id>/` (모두 암호화)
- `log/<기기ID>/<순번 8자리>.rec` : 그 기기가 한 번 올린 변경 묶음(레코드 목록). 각 기기는 **자기 폴더에만 쓴다** → 서로 덮어쓰는 일이 없고, 순번이 기기마다 단조 증가하므로 `If-None-Match: *`로 충돌 없이 올린다.
- `img/<sha256>.enc` : 이미지.
- `ckpt/<기기ID>-<순번>.snap` : 그 시점의 전체 상태(새 기기 시작과 로그 정리용).
- `dev/<기기ID>.json` : 기기 목록·마지막 순번·마지막 접속(로그 정리 기준).
- 로컬에는 기기별 "여기까지 읽음" 순번 `cursor[dev]`를 둔다.

## 동기화 한 번의 순서
1. `dev/`와 각 기기의 `log/`를 목록 조회해 내 cursor보다 새로운 파일을 찾는다.
2. 새 묶음을 받아 복호화·검증(해시)한다. 실패한 묶음은 건너뛰지 않고 중단하고 보고한다.
3. 레코드마다 적용한다(아래 병합 규칙). 적용은 **멱등**이라 같은 묶음을 두 번 받아도 안전하다.
4. 내 dirty 레코드를 모아 묶음 하나로 암호화해 `log/<내 기기>/<다음 순번>.rec`에 올린다(없을 때만 쓰기). 이미지가 새로 생겼으면 먼저 올린다.
5. 성공하면 cursor와 base_json을 갱신하고 dirty를 지운다. 중간에 끊기면 아무 것도 확정하지 않아 다음에 다시 한다.

## 병합 규칙
- 한쪽만 바뀜: 바뀐 쪽을 채택.
- 양쪽 바뀜: 필드별로 base와 비교해 한쪽만 바꾼 필드는 그 값을, 양쪽이 다르게 바꾼 필드는 (ver, dev) 큰 쪽(제목·분류·핀 등)을 채택. **본문은 줄 단위 3-way 병합**: 안 겹치면 자동 병합, 겹치면 큰 쪽을 본문으로 하고 진 쪽 본문을 `제목 (충돌 · 기기 · 시각)` 문서로 저장한다(태그 `충돌` 자동 부여).
- 삭제 대 수정: **수정이 이긴다**(삭제된 문서를 휴지통으로 되살림). 데이터를 잃지 않는 쪽을 택한다.
- 분류 이동으로 순환이 생기면 순환을 끊도록 마지막으로 적용된 쪽 분류를 최상위로 올린다.
- 같은 ID가 아닌 같은 제목 문서는 그대로 둔다(제목 중복 허용 여부는 현재 앱 동작을 따른다).

## 첫 연결
- 새 저장소: 이 PC의 전 문서를 체크포인트로 올린다.
- 기존 저장소에 연결(다른 PC): 문서 ID가 서로 달라 내용을 자동 대응할 수 없으므로 선택한다 — "서버 내용으로 교체(현재 DB는 backup 보관)"(기본) / "합치기(서버 문서를 추가, 중복 가능)".

## 로그 정리
- 로그는 계속 쌓인다. 체크포인트를 주기적으로 만들고, 모든 기기가 지난 N일(기본 90일) 안에 그 체크포인트 이후 순번을 읽었다면 그 이전 로그를 지운다. 오래 접속하지 않은 기기는 체크포인트부터 다시 시작한다(그 사이의 로컬 변경은 3-way 병합으로 합류).

## 열려 있는 문서
- 편집 중인 문서에 원격 변경이 오면 저장된 편집 내용과 먼저 병합하고, 결과를 편집기에 반영한다(커서는 병합 전 위치를 줄·글자 오프셋으로 보정). 되돌리기 기록은 이때 초기화된다(알림 표시).

## 단계(세션 분리)
1. **로컬 모델**: 스키마 v4 마이그레이션(uid·ver·dev·dirty·base_json·tombstones), DB 쓰기에서 dirty 표시, 테스트. 네트워크 없음.
2. **동기화 핵심(순수 로직)**: 레코드 코덱과 암호화(`vault` 키 재사용), 로그 읽기/쓰기, 적용과 병합, 충돌 사본, 삭제 표식, 순환 끊기, 체크포인트·시작. 메모리 `Remote`로 테스트. 3개 복제본에 무작위 편집을 섞어도 **모두 같은 상태로 수렴**하는지 확인하는 테스트가 핵심.
3. **전송과 UI**: 기존 `WebDavRemote` 재사용(목록·올리기·읽기), 동기화 창에 "문서 단위" 방식, 충돌 사본 안내, 첫 연결 선택, 상태 표시.
4. **보강**: 이미지, 로그 정리, 큰 DB 성능, 열려 있는 문서 반영, 도움말·서버 가이드.

## 검증 계획
- 수렴 테스트(무작위 편집·순서 뒤섞기·같은 묶음 중복 적용), 끊긴 올리기 후 재시도, 틀린 키·변조된 묶음 거부, 삭제 대 수정, 분류 순환, 3-way 병합 경계(겹침·인접 줄).
- 통합: 로컬 WebDAV와 사용자의 시놀로지에서 두 데이터 폴더(`AKASHIC_DATA`)로 실제 교차 편집.

## 위험
- `uid` 추가와 모든 쓰기 경로의 dirty 표시가 누락되면 변경이 전파되지 않는다(1단계 테스트로 모든 쓰기 경로를 점검).
- 열려 있는 문서에 원격 변경을 반영할 때 egui `TextEdit`의 커서·입력 중복.
- 두 PC의 기존 DB를 합치는 첫 연결은 중복 문서가 생길 수 있다.
- 작업량: 새 코드 3,000~4,000줄, 세션 4개 분량(스냅숏 WebDAV 작업의 2~3배).

## 결정이 필요한 것(기본값)
1. 병합 방식: A(3-way) — B(CRDT)는 후속.
2. 삭제 대 수정: 수정이 이김.
3. 첫 연결: 기본은 "서버 내용으로 교체".
4. 기존 스냅숏 방식 유지: 예.

## 구현 중 변경
- **버전은 Lamport(`ver`+`dev`) 대신 버전 벡터(`vv`: 기기→카운터)**. 마지막 쓴 쪽 비교만으로는 "서로 모르는 동시 편집"과 "한쪽이 다른 쪽을 포함"을 구분하지 못해, 동시 편집 하나가 조용히 사라질 수 있었다. 그래서 DB 열도 `ver`·`dev` 없이 `uid`·`dirty`·`base_json`(마지막 동기화 상태 = 버전 벡터 포함 레코드)만 둔다. 삭제 표식 `tombstones(uid, kind, base_json, dirty)`.
- **태그는 `uid` 없이 이름으로 식별**(이미 유일). 문서 레코드는 `tags: [이름]`. 태그는 집합 병합(양쪽이 더한 것은 합치고, 한쪽이 지운 것은 지움).
- **레코드에 `parent`(직전 상태)를 함께 싣는다**: 서로 모르는 동시 편집을 받은 쪽이 3-way 병합의 공통 조상으로 쓴다(받는 쪽이 조상 상태를 따로 기억하지 않아도 되도록). 올리는 크기는 바뀐 문서에 한해 약 두 배(deflate 압축 후 암호화).
- **서버 배치는 하위 폴더가 아니라 평평한 이름**(`Remote` 트레이트가 폴더 없는 이름만 다룸): `log-<기기>-<순번8>.rec`, `ckpt-<기기>-<순번>-<기기>.<읽은순번>-….snap`(이름에 "각 기기 로그를 어디까지 담았는지"를 넣어 받지 않고 고름), `dev-<기기>.json`, `img-<해시>.enc`. 서버 폴더는 `akashic2-<vault-id>`(스냅숏 방식 폴더와 분리). 파일은 JSON → deflate → 이름에 묶인 XChaCha20-Poly1305(`vault::seal_named`).
- **첫 연결 "새 저장소"는 체크포인트가 아니라 일반 로그 1번**으로 올린다(별도 경로 없이 같은 코드를 쓴다). 체크포인트는 로그가 50번 쌓일 때마다 만든다.
- **같은 문서 충돌 사본은 내용에서 uid·제목·시각을 정해(UTC)** 두 PC가 같은 사본을 만들어 중복되지 않게 한다. 제목의 시각은 UTC 기준이다.
- **삭제 표식은 본 삭제들의 버전을 합쳐 보관**(옛 삭제가 늦게 도착해 더 새로운 삭제를 덮는 것을 막음). 삭제를 만났지만 수정이 이겨 문서를 유지할 때는 내용이 같아도 다시 올려 다른 PC가 되살리게 한다(`force`).
- **분류 순환은 각 순환에서 uid가 가장 작은 분류를 최상위로** 올려(결정적) 모든 PC가 같게 끊고, 그 수정은 일반 변경으로 올린다. (설계의 "마지막으로 적용된 쪽"은 PC마다 달라 수렴하지 않는다.)
- **로그 정리**: 체크포인트가 이름에 담은 순번과 활성 기기(90일 안 접속)가 읽은 순번 중 작은 값까지만 지우고, 다른 체크포인트에 완전히 덮인 옛 체크포인트를 지운다. 기기 파일이 없는 기기의 로그는 지우지 않는다.
- UI는 새 방식 이름 "문서 단위(WebDAV)"(`sync_mode = "webdoc"`), 기존 "전체 스냅숏(WebDAV)"은 `"webdav"` 그대로. 자동 동기화는 이 PC에 바뀐 것이 있으면 10분마다.
- **스키마 번호**: 설계의 "v4"는 구현에서도 v4다(커밋된 `SCHEMA_VERSION`은 3이었고 이번에 4로 올림). 승급은 되돌릴 수 없으므로(옛 버전은 새 스키마를 열지 못함) 기존 DB(v1~v3)를 처음 열 때 **승급 직전에 `backup/vault-before-v4-<시각>.db`로 자동 백업**하고, 백업이 실패하면 승급하지 않고 오류를 돌려준다. v4 승급 본체는 한 트랜잭션이라 중간에 끊겨도 다시 열 수 있다.
